'@fantasticfour/world-nats-jetstream': minor
---

Add an `ackWaitMs` option for the JetStream consumers. Workers extend a delivery's ack deadline with `working()` heartbeats sent from their own event loop, so a step that blocks that loop for longer than the ack wait (30s by default) misses its heartbeats, and JetStream redelivers the message to another worker while the first execution is still running, spending a delivery from `max_deliver` each time. A consumer whose steps run long synchronous work can now set an ack wait that outlasts them. Heartbeats now fire every third of the ack wait the server reports for the shared durable consumer instead of a fixed 10s, and each stream re-reads that value every 5s, so a worker started with a different `ackWaitMs` follows a change another process makes and heartbeats immediately when the interval shrinks. An existing durable consumer keeps its ack wait unless `ackWaitMs` is set, in which case the value is rewritten and a warning names the value it replaced, so two processes with different settings no longer flap it on every restart. Workers now pull one message at a time instead of buffering up to 100, since a buffered delivery's ack wait ran down with no heartbeat behind a long-running step: the in-flight ceiling per stream is now `queueConcurrency` (10 by default), and each message costs one pull round trip, so raise `queueConcurrency` for throughput. A pull that fails with a transient JetStream status is now retried in place with escalating backoff instead of tearing the worker and its consumer setup down, and a worker's failure counter only resets after a delivery succeeds. A stream that cannot read its consumer info backs the refresh off to 60s and logs once, then picks the ack wait back up on its own when the server answers again. Values outside 1000 ms to 24 days throw a RangeError at construction. Unset, the 30s ack wait applies as before.
